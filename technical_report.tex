\section{Executive Summary}
This document presents the formal technical report for the \textbf{P2P Web Share} project. Traditional file-sharing services rely heavily on centralized servers to host, process, and distribute files, which incurs substantial bandwidth costs and poses inherent privacy risks. This project addresses these shortcomings by delivering a lightweight, secure, and fully decentralized peer-to-peer (P2P) file-sharing web platform. 

The application facilitates direct browser-to-browser file transfers without retaining, processing, or storing any portion of the file payload on a centralized server. This report comprehensively details the system architecture, the technology stack utilized, deep implementation mechanics of the Minimum Viable Product (MVP), and the cryptographic measures employed to ensure data integrity.

\section{Problem Statement}
In conventional client-server architectures, when a user shares a file, the file must first be uploaded entirely to a server. The receiver then downloads the file from that same server. This paradigm has several drawbacks:
\begin{itemize}
    \item \textbf{Privacy Concerns:} The central server has full access to the unencrypted file data unless zero-knowledge encryption is explicitly implemented.
    \item \textbf{Bandwidth Costs:} The server incurs bandwidth costs for both the inbound upload and the outbound download.
    \item \textbf{Storage Limitations:} Servers must allocate massive storage arrays to temporarily house files waiting to be downloaded.
\end{itemize}
The objective of this project is to bypass the server entirely for the data transfer phase. The system must establish a direct data tunnel between the sender's device and the receiver's device. A central server is only permitted for the initial connection brokering (signaling), after which it steps out of the loop.

\section{System Architecture}
The system architecture of the P2P Web Share application is a hybrid model. It utilizes a centralized star topology strictly for signaling, but transitions to a decentralized mesh (1-to-1) topology for the actual data transfer. 

\subsection{Frontend Client Architecture}
The frontend is a single-page application (SPA) executed entirely within the user's web browser. It is responsible for:
\begin{itemize}
    \item Reading local file data securely using the \texttt{FileReader} and \texttt{Blob} APIs.
    \item Maintaining the state of the WebRTC \texttt{RTCPeerConnection} and \texttt{RTCDataChannel}.
    \item Handling all cryptographic hashing operations locally.
    \item Rendering a responsive, real-time user interface that reflects the state of the active connection and data stream throughput.
\end{itemize}

\subsection{Signaling Server Architecture}
The backend consists of a minimalistic Node.js server. Its sole responsibility is to act as a discovery and negotiation broker.
\begin{itemize}
    \item It coordinates the initial WebRTC connection handshake by relaying Session Description Protocol (SDP) offers and answers.
    \item It routes Interactive Connectivity Establishment (ICE) candidates between peers to traverse NATs and firewalls.
    \item It maintains lightweight state regarding active "Rooms" but enforces a strict two-peer limit per room. It operates entirely blind to the binary file transfer channel.
\end{itemize}

\section{Technology Stack}
The application leverages a modern web technology stack carefully chosen to support real-time communication and robust frontend state management:

\begin{itemize}
    \item \textbf{Frontend Framework:} React.js. Chosen for its component-driven architecture and efficient DOM reconciliation, which is critical when updating high-frequency UI components like progress bars.
    \item \textbf{Styling and Aesthetics:} Custom vanilla CSS utilizing CSS Variables, responsive grid layouts, and glassmorphism design principles tailored for a premium dark mode experience.
    \item \textbf{P2P Communication:} Native Browser WebRTC API. This provides the underlying UDP/TCP transport layer necessary for traversing NATs and establishing the direct data channel.
    \item \textbf{Signaling Backend:} Node.js with Express.js and Socket.io. Socket.io provides persistent, full-duplex WebSocket connections with automatic fallback to long-polling if necessary.
    \item \textbf{Cryptography:} Native Web Crypto API (\texttt{crypto.subtle.digest}). This provides highly optimized, non-blocking hardware-accelerated SHA-256 hash generation directly in the browser.
    \item \textbf{Build Tool:} Vite. Utilized for fast hot-module replacement during development and optimized, minified bundling for production deployment.
\end{itemize}

\section{Feature Implementation Details}

\subsection{Share Room Creation \& Link Generation}
The entry point of the application requires the sender to initialize a secure transfer room.
\begin{itemize}
    \item \textbf{Mechanism:} The interface provides a drag-and-drop zone. When a file is selected, the application validates its size against a hardcoded limit of 50 MB (\texttt{50 * 1024 * 1024} bytes). This constraint ensures that the standard browser RAM limit is not exceeded during the reassembly phase of the MVP.
    \item \textbf{Room Allocation:} Upon valid file selection, the client invokes \texttt{crypto.randomUUID()} to generate a secure, collision-resistant unique Room ID. 
    \item \textbf{Outcome:} A unique invite link is generated (e.g., \texttt{https://domain.com/room/[ROOM\_ID]}) and presented to the sender. This URL is used to invite the receiving peer.
\end{itemize}

\subsection{Signaling Handshake Process}
To establish a direct connection, peers must first discover each other and negotiate network parameters through the signaling server.
\begin{itemize}
    \item \textbf{Event Flow:}
    \begin{enumerate}
        \item The sender emits a \texttt{create-room} Socket.io event to the server.
        \item The receiver navigates to the invite link and emits a \texttt{join-room} event.
        \item The server registers the receiver and broadcasts a \texttt{peer-joined} event back to the sender.
        \item The sender instantiates an \texttt{RTCPeerConnection}, generates an SDP Offer, and transmits it via the server's \texttt{signal} event.
        \item The receiver accepts the SDP Offer, generates an SDP Answer, and transmits it back.
        \item Simultaneously, both clients generate and exchange ICE candidates to establish the optimal direct network path (via STUN/TURN servers if necessary).
    \end{enumerate}
    \item \textbf{Security:} The signaling server enforces a strict two-peer limit per room. It solely passes JSON metadata and never interfaces with the WebRTC data channel.
\end{itemize}

\subsection{Direct P2P Data Transfer \& Streaming}
Once the WebRTC tunnel is established, the application initiates the file stream.
\begin{itemize}
    \item \textbf{Data Channel:} The sender opens an \texttt{RTCDataChannel} labeled \texttt{file-transfer}. Critically, the channel is configured with \texttt{ordered: true}. This guarantees that packets arrive in the exact sequence they were sent, which is mandatory to prevent file corruption over unreliable UDP networks.
    \item \textbf{Memory-Safe Streaming:} To prevent browser UI thread blocking and memory exhaustion, the file is not loaded entirely into RAM at once. Instead, it is asynchronously sliced into \texttt{32 KB} chunks using the \texttt{Blob.slice()} API and converted into an \texttt{ArrayBuffer} just before transmission.
    \item \textbf{Buffer Management (Backpressure):} The application continuously monitors the \texttt{bufferedAmount} of the data channel. If the sender's network speed outpaces the receiver's download speed, the internal buffer fills up. If it exceeds a predefined threshold (e.g., 256 KB), transmission is paused using an await loop tied to the \texttt{bufferedamountlow} event listener. This prevents packet loss and buffer overflow.
\end{itemize}

\subsection{Cryptographic Verification \& Integrity}
Data corruption is a common issue in peer-to-peer streaming due to dropped packets or network interference. To mitigate this, rigorous cryptographic checks are enforced throughout the lifecycle of the transfer.
\begin{itemize}
    \item \textbf{Pre-computation:} Before initiating the stream, the sender computes a master SHA-256 hash for the entire file. Additionally, as each 32 KB chunk is prepared, a localized SHA-256 hash is generated.
    \item \textbf{Transmission:} The sender transmits a JSON \texttt{chunk-header} containing the chunk index, chunk size, and its expected hash. This control message is immediately followed by the raw binary \texttt{ArrayBuffer}.
    \item \textbf{Validation:} The receiver intercepts the binary data, computes its own SHA-256 hash using the Web Crypto API, and strictly matches it against the expected hash in the preceding header. If a mismatch occurs, a \texttt{chunk-nack} (Negative Acknowledgement) is fired, and the chunk is rejected.
    \item \textbf{Final Check:} Upon receiving the final chunk, the receiver merges the chunks and computes a new SHA-256 hash over the entire reassembled Blob. This final hash is checked against the master hash provided at the start of the session to guarantee zero corruption.
\end{itemize}

\subsection{Real-Time Progress Indicators}
The User Interface is deeply integrated with the React state to provide continuous feedback without dropping frames.
\begin{itemize}
    \item \textbf{Metrics Tracked:} The state maintains a \texttt{transfer} object that tracks \texttt{totalBytes}, \texttt{transferredBytes}, \texttt{totalChunks}, and \texttt{verifiedChunks}.
    \item \textbf{Speed Calculation:} By capturing a \texttt{performance.now()} timestamp at the beginning of the transfer, the application accurately calculates the exact throughput in Megabytes per second (MB/s).
    \item \textbf{Dynamic Status:} The UI connection status dynamically updates through various phases: "Waiting for receiver", "Negotiating direct connection", "Transferring", "Verifying", and "Complete".
\end{itemize}

\subsection{Graceful Disconnect \& Error Handling}
Network instability is handled proactively to avoid application crashes or silent freezes.
\begin{itemize}
    \item \textbf{Event Listeners:} The \texttt{RTCPeerConnection} continuously monitors the \texttt{onconnectionstatechange} event. Concurrently, the Socket.io signaling server listens for abrupt WebSocket disconnections.
    \item \textbf{Execution:} If a user closes the tab, refreshes the page, or loses internet access, the server detects the broken socket and emits a \texttt{peer-disconnected} event to the remaining peer in the room.
    \item \textbf{Resolution:} The remaining client's UI immediately halts the transfer loop, displays an alert stating "Peer disconnected. The transfer has stopped.", and cleans up local WebRTC objects (\texttt{dataChannel.close()}) to prevent memory leaks.
\end{itemize}

\subsection{Automated Memory Assembly \& Download}
The final phase of the transfer ensures a seamless user experience that mimics a traditional download.
\begin{itemize}
    \item \textbf{Blob Construction:} Once all chunks are verified and acknowledged, the array of \texttt{ArrayBuffer}s is passed into a single \texttt{Blob} object, inheriting the original file's MIME type from the initial metadata payload.
    \item \textbf{Triggering the Download:} The application invokes \texttt{URL.createObjectURL(blob)} to generate a temporary localized download link referencing the browser's memory. A hidden \texttt{<a>} (anchor) element is injected into the Document Object Model (DOM), assigned the original (sanitized) filename, and programmatically clicked via JavaScript.
    \item \textbf{Cleanup:} Immediately following the download trigger, the anchor is removed from the DOM, and \texttt{URL.revokeObjectURL()} is called to release the memory consumed by the Blob URL, preventing the browser tab from crashing due to memory bloat over multiple transfers.
\end{itemize}

\section{Scalability \& Limitations}
While the MVP successfully achieves its objectives, it operates under certain deliberate constraints:
\begin{itemize}
    \item \textbf{File Size Limit:} The current implementation restricts file sizes to under 50 MB. This is because the receiver stores the incoming chunks entirely in RAM (as an Array of ArrayBuffers) before compiling them into a Blob. For files exceeding a few hundred megabytes, this approach risks crashing the browser tab due to memory exhaustion.
    \item \textbf{Network Traversal:} The application currently relies on public Google STUN servers (\texttt{stun.l.google.com:19302}). While effective for most consumer NATs, strict enterprise firewalls or symmetric NATs require TURN servers to relay the traffic. Without a dedicated TURN server, peer connections may occasionally fail in highly restrictive network environments.
\end{itemize}

\section{Future Enhancements}
To elevate the platform beyond the MVP stage, several advanced features are planned:
\begin{itemize}
    \item \textbf{Large File Support ($>$500MB):} To bypass standard browser RAM limitations, incoming chunks can be written directly to local disk storage using the Streams API paired with the Origin Private File System (OPFS). This would allow the transfer of multi-gigabyte files without memory spikes.
    \item \textbf{Zero-Knowledge Encryption:} While WebRTC data channels are encrypted in transit via DTLS/SRTP, adding an application-layer encryption mechanism would provide an extra layer of security. The file chunks could be encrypted in the browser using the Web Crypto API (AES-GCM) before transmitting. The decryption key could be passed purely via the URL hash (e.g., \texttt{/\#key=...}) so neither the signaling server nor any intermediary ever has access to the raw file data.
    \item \textbf{Connection Churn Recovery (Auto-Resume):} Implementing a state-tracking handshake would allow a dropped connection to automatically pause and resume from the last verified chunk once the peer reconnects, rather than restarting the transfer from 0\%.
\end{itemize}

\section{Conclusion}
The P2P Web Share project successfully implements a highly secure, decentralized file-transfer platform. By maximizing the capabilities of the modern browser---specifically the WebRTC API for peer-to-peer streaming and the Web Crypto API for strict data integrity validation---the application achieves reliable, serverless data transfer. 

The implementation elegantly balances robust technical constraints, such as backpressure management and memory safety, with a highly responsive, modern user interface. By successfully eliminating the need for centralized storage, the platform guarantees data privacy while reducing infrastructure costs to near zero, fulfilling all Minimum Viable Product specifications effectively and providing a strong foundation for future advanced feature integrations.
